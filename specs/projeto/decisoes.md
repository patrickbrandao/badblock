# Decisões

Registro das decisões de projeto: o que foi decidido, quando e por quê. Uma
decisão nova entra no fim; uma que muda outra a cita. Antes de propor o
contrário de uma decisão daqui, leia o motivo.

| # | Data | Decisão | Motivo |
|---|---|---|---|
| 1 | 2026-09-28 | Redesign para simplificar: tudo o que existia foi para `old/` (fora do git); a fase 1 recomeçou com um par coletor/API por fonte | A versão anterior (registry-sync/registry-api) misturava fontes e responsabilidades |
| 2 | 2026-09-28 | Coletor e API são apps separados, sem código compartilhado; o contrato é o banco | Deploy, teste e evolução independentes; nenhuma mudança num app quebra outro |
| 3 | 2026-09-28 | Prefixo das tabelas = nome da fonte (`cgibr_*`), não o nome do app | Nomes SQL sem hífen; o mesmo nome nos dois apps |
| 4 | 2026-09-28 | Postgres dedicado, todos os serviços com o usuário `postgres` no banco `badblock`, só por `POSTGRES_URL`; sem roles, `GRANT`, bootstrap nem backup | Simplicidade: os dados são descartáveis e recarregáveis das fontes |
| 5 | 2026-09-28 | dbmate com uma pasta por fonte e tabela de controle `<pasta>_schema_migrations`; `central/` sempre primeiro | Cada fonte evolui o schema sozinha, sem conflito de numeração |
| 6 | 2026-09-28 | Tabela `jobs` com `consolidated` 0/1 como contrato com a fase 2 | A consolidação futura sabe o que mudou sem conhecer cada fonte |
| 7 | 2026-09-28 | Imagens distroless não-root; healthcheck da API pelo próprio binário (`healthcheck`) | Superfície mínima: a imagem não tem shell nem curl |
| 8 | 2026-09-28 | Containers internos com `traefik.enable=false` | O Traefik do servidor publica todo container por padrão (`exposedByDefault`) |
| 9 | 2026-09-28 | Scripts de operação do mantenedor fora do git; só `release-images.sh` versionado; `run-server.sh`/`run-builder.sh` não se editam sem pedido explícito | Guardam valores do ambiente dele; o repositório é público |
| 10 | 2026-09-29 | Cada RIR é uma fonte (`afrinic`, `apnic`, `arin`, `lacnic`, `ripencc`), não uma fonte `rir` com cinco arquivos | O nome da fonte é um token sem hífen que casa com `jobs.app`; cada RIR publica e muda num ritmo próprio |
| 11 | 2026-09-29 | Os cinco pares de RIR são o mesmo código, clonado do lacnic; o específico fica em `internal/rir/rir.go` | Mesmo formato (delegated-extended); sem código compartilhado entre apps (#2) |
| 12 | 2026-09-29 | `compose.wait-migrate/` é uma pasta com um override por coletor | Um override único com vários serviços cria serviços sem imagem em cada `include` |
| 13 | 2026-09-29 | `collector-iana` verifica a cada 6h | A IANA muda poucas vezes por ano e o Cloudflare guarda os arquivos por 1h/24h (ver `specs/fontes/iana/collector.md`) |
| 14 | 2026-09-29 | Toda API tem manifesto OpenAPI 3.1 embutido; a v1 fixa é um *servidor*, não caminhos `/v1` duplicados | Caminhos duplicados repetiriam `operationId`, o que a especificação proíbe |
| 15 | 2026-09-29 | Apps agrupados por fonte: `apps/<fonte>/collector/` e `apps/<fonte>/api/` (antes `apps/collector-<fonte>/`); nomes de app, imagem, container, tag e `jobs.app` mantidos | Um site com vários conjuntos de dados fica numa pasta só; nada muda em produção |
| 16 | 2026-09-29 | Specs centralizadas em `specs/` (fora dos apps), em camadas: projeto, plataforma, padrões, fontes (com um modelo único para os RIRs) e processos; `AGENTS.md`/`CLAUDE.md` só com regras de trabalho e o mapa | As specs têm de permitir reconstruir o projeto mesmo se o código for apagado, sem repetir o mesmo texto em 16 lugares |
| 17 | 2026-09-29 | O manifesto OpenAPI continua dentro do app, derivado da spec | O `go:embed` não enxerga fora do módulo e o build usa só a pasta do app |
| 18 | 2026-09-30 | Os três arquivos da raiz do DNS são três fontes: `roothints` (`named.root`), `rootzone` (`root.zone`) e `rootanchors` (`root-anchors.xml`), cada uma com o seu par de apps; nenhuma entra na `iana` nem numa fonte `internic` | Cada arquivo muda num ritmo próprio (`root.zone` cerca de 2 vezes por dia; os outros, poucas vezes por ano), como os RIRs (#10); assim não é preciso fechar a questão de vários conjuntos por site (abaixo) |
| 19 | 2026-09-30 | Sites em `websites/<site>/`, app `website-<site>`: Vite + React + Tailwind (JavaScript), build em `dist/` servido na raiz do host por lighttpd não-root no Alpine; o `www` responde pelo domínio puro e pelo `www`, sem redirecionar um para o outro | Sem servidor Node em produção (menos superfície, imagem pequena); cada site implantado sozinho, como os outros apps |
| 20 | 2026-09-30 | Dependências Go vendorizadas (`vendor/` versionado em cada app); o Dockerfile copia só a pasta do app e compila com `GOFLAGS=-mod=vendor GOPROXY=off`, sem `go mod download` | O build da imagem usa só os arquivos do projeto e não busca nada no GitHub nem no proxy do Go; as versões das dependências são as que estão no git. O `vendor/` igual entre apps não pesa no repositório (o git guarda cada arquivo uma vez) |
| 21 | 2026-09-30 | Site com vários conjuntos de dados: cada conjunto é uma fonte de **dois níveis**, `<site>/<conjunto>` (ex.: `anatel/pst`), com o seu par de apps. O caminho (pastas, specs, HTTP) usa `/`; nomes de app, imagem, container, tag e `jobs.app` usam `-` (`collector-anatel-pst`); nomes SQL (tabelas, pasta de migrations) usam `_` (`anatel_pst_*`); variáveis usam `_` em maiúsculas (`API_ANATEL_PST_*`). Fecha a questão em aberto de vários conjuntos por site | A Anatel publica vários conjuntos independentes (cada um com formato e ritmo próprios, como #10 e #18); agrupá-los por site mantém `apps/anatel/` e `specs/fontes/anatel/` juntos, e cada forma do nome continua válida onde é usada (SQL sem hífen, `jobs.app` sem `_`) |
| 22 | 2026-10-02 | O `asn.txt` do RIPE NCC passa a ser a fonte de dois níveis `ripe/asnames` (antes `asnames`): apps `collector-ripe-asnames` e `api-ripe-asnames`, caminho `/ripe/asnames/`, tabelas `ripe_asnames_*` | O arquivo é publicado pelo RIPE NCC (`ftp.ripe.net/ripe/asnames/`) e deve ficar no domínio do RIPE; as delegações continuam na fonte de um nível `ripencc` (família RIR) |
| 23 | 2026-10-02 | `run-builder.sh` sai; o build local fica em `run-build.sh` (`docker build`, arquitetura local) e `run-buildx.sh` (`docker buildx`, amd64 + arm64), ambos com tag `yyyy-mm-dd-HHMM` + `latest` (`VERSION` e `BUILD_DATE` fixos, editados à mão a cada versão, para não invalidar o cache) e atualizados junto com o `docker-compose.yml`; todo `run-*.sh` é privado do desenvolvedor e fica fora do git; só `run-server.sh` segue sem edição sem pedido explícito | Separar build de execução e ter imagens multi-arch sem depender do `release-images.sh` |
| 24 | 2026-10-10 | Fonte `rdns`: o BadBlock varre ele mesmo o reverso (PTR) de todo IPv4 dos prefixos cadastrados (`collector-rdns`, `api-rdns`, tabelas `rdns_*`, `/rdns/`, porta 8113). É uma **sonda ativa**, com padrão próprio em `specs/padroes/sonda.md`, só do coletor (os desvios da API ficam no `api.md` da fonte). O coletor **lê** as tabelas do `cgibr` (`cgibr_run`, `cgibr_prefix`, `cgibr_asn`) para derivar os prefixos, sem escrever nelas | Não há arquivo publicado com o reverso; derivar do `cgibr` dá a lista de blocos brasileiros com ASN sem uma fonte nova. Ler outra fonte não cria código compartilhado (#2): o contrato continua sendo o banco |
| 25 | 2026-10-10 | `rdns_prefix` guarda o cadastro **e** o estado da varredura em colunas (`scan_worker`, `scan_started_at`, `last_scan_at`, contadores); os blocos IPv4 do `cgibr` entram quebrados em /24, as linhas `static` são do administrador. Prefixos só entram sozinhos, nunca saem sozinhos: remover, ativar, desativar e pedir nova varredura é do sistema de gestão do administrador, que escreve direto no banco. A regra "IPv4 de /22 a /24" fica só no software; `updated_at` só anda em mudança de cadastro | O /24 é a unidade de delegação reversa e cabe no lease; a fila é a própria tabela (sem outra estrutura para sincronizar); um bloco que some do `cgibr` pode ainda ser útil, e quem decide é o administrador |
| 26 | 2026-10-10 | O banco proíbe prefixos sobrepostos em `rdns_prefix` (`EXCLUDE USING gist (prefix inet_ops WITH &&)`); um trigger `BEFORE INSERT` quebra o prefixo novo que sobrepõe outros nos /24 que faltam (herdando o cadastro) e descarta o já coberto; um trigger `AFTER DELETE` apaga de `rdns_ptr` os IPs do prefixo removido | O administrador grava direto no banco: a regra tem de valer para qualquer escritor, e um IP tem de pertencer a um prefixo só (a ligação IP → prefixo é por continência, sem coluna) |
| 27 | 2026-10-10 | `rdns_ptr` tem PK **natural** `ip inet` (exceção à PK `uuidv7()`); só IPs com PTR ou com falha têm linha (`NXDOMAIN`/NODATA = sem linha), uma falha nunca apaga um PTR, sem TTL, sem histórico e sem data por IP (a data é o `last_scan_at` do prefixo); a linha só é regravada quando muda | ~55 M linhas (~10 GB): uma PK `uuid` somaria bytes e um segundo índice por linha; guardar o `NXDOMAIN` dobraria a tabela; regravar o igual geraria ~79 M escritas por volta |
| 28 | 2026-10-10 | O `collector-rdns` roda em várias instâncias: fila em `rdns_prefix` com `FOR UPDATE SKIP LOCKED` e lease (`SCAN_LEASE`), uma linha por instância em `rdns_worker`, compose **sem `container_name`** e com `deploy.replicas: ${COLLECTOR_RDNS_REPLICAS:-1}`; instâncias em outros hosts alcançam o Postgres e o Valkey por um caminho de rede do operador, fora do repositório | 79,0 M endereços a 256 req/s levam ~86 h com um coletor; a meta de 24 h pede ~4, e cada host consulta pelos próprios resolvedores |
| 29 | 2026-10-10 | Taxa (`rate_limit`, **por coletor**) e meta (`scan_interval`) na tabela chave/valor `rdns_config`, relida a cada 30 s; `RATE_LIMIT` (256) e `SCAN_INTERVAL` (24h) no ambiente valem quando a linha falta ou não pode ser lida | O administrador muda a taxa de todos os coletores sem reiniciar nada; o coletor continua de pé com o banco sem a linha |
| 30 | 2026-10-10 | Tempo real do rdns por uma fila no Valkey (`badblock:rdns:live:queue`, sem TTL; a API faz `RPUSH`, o coletor `BLPOP`, e a resposta volta numa lista com 30 s de expiração e é gravada em `rdns_ptr`); a API continua sem escrever no Postgres. O Valkey passa de `allkeys-lru` a **`volatile-lru`** | A API pede sem ter cliente DNS nem escrever no banco; com `allkeys-lru`, a fila (sem TTL) poderia ser despejada com a memória cheia |
| 31 | 2026-10-10 | `shared_buffers` padrão do Postgres sobe de 512 MB para **2 GB** (`POSTGRES_SHARED_BUFFERS`) | O `rdns_ptr` (~10 GB, ~1,2 GB de índice) passa a ser a maior tabela do banco |
| 32 | 2026-10-10 | Dependência nova: `github.com/miekg/dns` v1.1.73, só no `collector-rdns` | O `net` da biblioteca padrão não controla EDNS0, `RD`, `DO`, o servidor de cada consulta nem devolve o `RCODE` (`SERVFAIL` × `REFUSED`) |
| 33 | 2026-10-10 | A `api-rdns` não tem versão de dataset: chaves de cache sem versão (`badblock:api-rdns:ip:<ip>`, `prefix:<cidr>`) com TTL de 1 h, ETag do FNV-1a do corpo, bloco `scan` no lugar de `dataset`; `/rdns/ip/{ip}?live=true` pede resolução na hora (5 s, depois o dado frio), com um segundo router no Traefik (`Query(live, true)`, 1 req/s, rajada 5); nenhuma rota por ASN | O dado muda um prefixo de cada vez, o dia inteiro: uma versão global invalidaria tudo a cada segundo; o tempo real custa uma consulta DNS e precisa de limite próprio; um ASN chega a 43.656 /24 |
| 34 | 2026-10-10 | O `make specs-check` aceita a pasta de uma fonte sem `apps/<fonte>/` quando o `README.md` dela traz a linha `> **Estado:** só specs` (e recusa a linha quando os apps existem) | A regra "spec primeiro" deixa a fonte só com specs entre os passos 2 e 4 de `nova-fonte.md`; sem a marca, a verificação falharia nesse intervalo |
| 35 | 2026-10-21 | O migrate roda de uma imagem própria, **`tmsoftbrasil/badblock-postgres-migrate`** (dbmate + `migrate.sh` + migrations em `/db`, `database/postgres/Dockerfile`), publicada pelo `release-images.sh`; o compose e o `run-server.sh` não montam mais `database/postgres` | O container de migrate acompanha a pilha em qualquer servidor só com o pull, sem levar arquivos do repositório junto |
